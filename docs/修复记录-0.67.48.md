## 2. 笔迹卡顿诊断（4096 大图上画时笔迹一段段出来）

现象：用户报 4096×3072 导出图上绘制卡顿、笔迹分段。缩放已不卡，说明问题在「一段笔迹的处理耗时」，不是重绘。

本版不猜，先把测量点放进程序：

- `SketchView.drawSegment` 拆成计时壳 + `drawSegmentInner`：每段计时，≥24ms 记为「慢段」。
- 一笔内累计：慢段次数、合计耗时、最慢单段；前 5 次直接 `Log.i("RevealPerf", "segment slow …")`。
- 抬手时把汇总写进日志：
  `笔迹慢: 工具 BRUSH 慢段 12 次 / 合计 1834ms / 最慢 260ms / 画布 4096x3072`

## 0.67.49 追加：区分「笔迹处理慢」还是「重绘慢」

0.67.48 的实测日志里**没有**「笔迹慢」这一行 → 说明每一小段的处理都 <24ms，卡不在笔迹算法，而在每帧重绘。
所以同一份汇总里补了绘制侧数据：

- `onDraw` 每帧计时（只在按着画的时候统计）：总帧数、慢帧数（≥24ms）、慢帧合计耗时。
- 抬手时写成：
  `笔迹慢: 工具 BRUSH 慢段 3 次 / 合计 96ms / 最慢 28ms / 画布 4096x3072 / 重绘 42 帧其中慢 30 帧(合计 1850ms)`
- 判读：重绘慢帧多、单帧 30~80ms → 是「每帧把 4096 图层重新上屏」的代价；慢段多 → 才是笔尖合成。

## 0.67.50 修正：上一版诊断没写进日志（我的门槛写错了）

0.67.49 的日志里连「笔迹慢」都没有，原因不是不慢，而是我把整条记录卡在 `慢段>0` 才写——笔迹段很快、只是重绘慢时，一条都不会写。

本版：
- 门槛改成「有慢段 **或** 有慢帧或统计到帧」就写。
- 多统计一项「图层上屏合计」（drawLayers 这段的累计耗时），用来确认是不是每帧把 4096 图层整张重传。

汇总格式：
`笔迹慢: 工具 BRUSH 慢段 3 次 / 合计 96ms / 最慢 28ms / 画布 4096x3072 / 重绘 42 帧其中慢 30 帧(合计 1850ms) / 图层上屏合计 1620ms`

判读：图层上屏合计占重绘的大头 → 改「笔画期间不逐段改图层、改画小图预览」；否则看慢段。

## 0.67.51 真因：每段把整幅 4096 缓冲交给 Skia

0.67.50 的日志给出了答案：

```
工具 BRUSH 慢段 8 次 / 合计 221ms / 最慢 31ms / 画布 4096x3072
/ 重绘 1 帧其中慢 0 帧 / 图层上屏合计 0ms
```

- 重绘帧几乎没统计（1~21 帧）、单帧都不超 24ms → **卡的不是上屏**。
- 每次抬笔都是 8 段左右、每段 26~31ms → **卡在每段的合成**。
- 定位到 `flushStrokeRect`：`cv.drawBitmap(buf, 0f, 0f, p)` 外面套了 `clipRect(r)`，但 Skia 仍要读整幅缓冲（4096×3072 = 50MB），一次移动 20~30ms，事件排队 → 笔迹一段一段往外冒。

本版改两处：
1. `cv.drawBitmap(buf, r, r, p)` —— 只把这一小块当源。
2. 大图（>1200 万像素）细分步长 `max(2.0, size*0.10)`（原来 1.2），每段盖章次数减半。

## 0.67.52 「不跟手」的第二层原因：画的时候在显示旧缓存

0.67.51 后慢段降到 0，但用户仍说「不跟手没变化」。看日志：`重绘 N 帧` 很少、单帧都不慢、`图层上屏合计 0ms` —— 说明落笔时 onDraw 根本没走「直接画图层」那条路，而是走了合成缓存（`!direct` 分支）。缓存是给静止画面用的，画到一半它还是旧的，于是笔迹要等缓存重建才出现 → 手感就是「不跟手、一段段冒」。

改：`val direct = canDrawDirect() || zooming || drawing` —— 落笔期间一律直接画图层。

同时把每次 ACTION_MOVE 的总耗时与其中「合成」耗时也写进日志（`移动 N 次合计 …ms(其中合成 …ms) / 慢事件 …`），下一次就能区分「事件处理慢」还是「上屏慢」。

## 怎么验

1. 打开 4096 那张工程，画一笔（拖长一点）。
2. 顶部「日志」→ 复制 → 发我。
3. 看有没有「笔迹慢」这一行，以及慢段次数/最慢单段。

正常（小画布）应该**没有**这行——说明只在大画布上慢，据此决定是改笔尖合成方式还是分块落笔。
