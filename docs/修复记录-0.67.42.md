# Reveal 0.67.42 修复记录（大图打开慢）

## 现象
`10_大图4096.psd`（37.8MB、4096×4096）打开要几分钟。

## 根因：RLE 解码是「一个字节一次 JNI」

PSD 的图层像素几乎都是 RLE（PackBits）压缩的。原来的解码循环长这样：

```kotlin
val n = c.byteInt(c.p++).toByte().toInt() and 0xFF
repeat(cnt) { out[...] = c.byteInt(c.p++).toByte() }
```

小文件时 `Cur` 背后是普通 ByteArray，一字节一次数组访问没问题；
但 24MB 以上走的是 `MappedByteBuffer`（off-heap 内存映射），每一次 `m.get(i)` 都是一次 **JNI 调用**。

4096×4096 一张图 = 1600 万像素，四通道就是 **6700 万次 JNI**，再乘上每层。
这就是「几分钟」的来源 —— 不是算法慢，是跨界调用慢。

## 改法

**1. RLE 整段拷贝再解**（`PsdIo.readRle` / `readRleRows`）

行表读完后就能算出这段压缩数据一共多少字节，一次性 `c.take(need)` 拷进 ByteArray，
然后纯在内存里解 PackBits。JNI 调用从「每字节一次」降到「每通道一次」。

**2. `Cur.byteInt` 加 256KB 滑动窗口**

映射文件的其他随机读也不再一字节一次 JNI：窗口没命中才 `duplicate().position().get()` 读 256KB，
顺序读基本只在换块时碰一次系统调用。

## 验收
1. 打开 `10_大图4096.psd` —— 应该从「几分钟」降到十几秒量级。
2. 打开后画几笔、存盘、杀进程重开 —— 正常。
3. 打开小图（01/05）—— 不受影响，仍正常。
4. 首页日志里能看到分段时间，把这两行发我：

```
RevealPerf: import xxx.psd 38666KB layers=N parse=...ms save=...ms
RevealPerf: save layers=N 4096x4096 encode=...ms zip=...ms thumb=...ms total=...ms
```

如果 `parse=` 仍然很大，下一步做「解析时按层并行 / 只解可见层」；如果 `save=` 大，就把 4096 的存储改成分块写入或延后存盘。

## 没做
- 没有做「懒解码」（打开只解当前可见层），因为会影响导出与图层操作的一致性，等日志数据再定。
- 没有做瓦片金字塔 mip 层级。
