# 修复记录 0.67.54

## 从 0.67.53 的日志读出来的事实

```
工具 BRUSH 慢段 0 次 / 合计 0ms / 画布 4096x3072
重绘 154 帧其中慢 0 帧(合计 0ms) / 图层上屏合计 0ms
移动 156 次合计 4896ms(其中合成 0ms) / 慢事件 62
```

- 合成 0ms、重绘 0 慢帧、图层上屏 0ms → **绘制和合成都不慢了**（0.67.53 的大图层改动生效了）。
- 但 `移动 156 次合计 4896ms` = **每次移动约 31ms**，卡在**触摸事件处理**里。

## 手机绘画软件的成熟做法（查证）

- **MyPaint / libmypaint 的 TiledSurface**：像素存在 64×64 的瓦片里，只给画到的瓦片分配内存；
  落笔时「被笔迹碰到的瓦片整体重合成，但**更新区域只裁到新 dab 的包围盒**」。
  （官方文档 Surface Format and Rendering 原文：*During painting, all tiles touched by the stroke are composited completely, but the update region is clipped to the bounding box of the new dabs.*）
- **Krita / Procreate / Infinite Painter**：落笔期间笔迹画在独立的小表面（stroke layer）上，抬手才合并进大图层。
- Android 官方 Slow rendering：位图内容一变就要整张重新上传纹理；按脏矩形 `invalidate(Rect)` 只重绘该区域。

## 这一版改了什么

1. **预览块改成「只拷这一段新加的那块」**。
   上一版每段都把「整笔的包围盒」从缓冲拷到预览块——一笔画长了，第 N 段就要拷 N 份面积，
   是平方级开销：单段几十毫秒，正好对上日志里 31ms/次。现在只拷本段的 dab 包围盒（几百毫秒→几毫秒）。
2. **缓冲复用不再整幅清零**。以前每笔开始 `eraseColor(0)` 是一次 50MB memset（4096 上），
   现在只清上一笔画到的那块（和 MyPaint「只碰瓦片」一致）。
3. **加了更细的计时**：日志里现在多了 `盖章 xms / 预览拷贝 xms`，
   下次卡的话，把「笔迹慢」那行发我，就能立刻判断是盖章慢还是拷贝慢，还是剩下的触摸/刷新。

## 怎么验
1. 4096 上拖一道**很长的**线（越长越能暴露平方级问题）：应该跟手，越画越顺。
2. 连续画十几笔（每笔都会触发一次缓冲清理）：笔与笔之间不该有顿挫。
3. 看日志「笔迹慢」那行的 `移动 N 次合计 Xms`：应该从 31ms/次 降到个位数。
