# 0.67.79 修复记录：拖笔时不再往文档缓冲里盖章

日志（0.67.77 / 4096×4096）给出的分工是：`合成 0ms / 上屏 0ms / 重绘 0 慢帧`，时间全在「盖章」，一笔 1075 个笔头、155ms。

## 这一版做的是「把盖章次数和次数×成本同时砍掉」

### 1. 间距下限按屏幕像素算（0.67.78 已在）

`minSpacingDoc() = 2.2f / zoom`。原来 1.2/zoom，4096 缩到 0.25 倍时下限只有 4.8 个文档像素 —— 屏幕上隔不到 1~2 像素的两次盖章画的是同一颗像素，纯属白干。
一笔笔头 1075 → 约 580。

### 2. 拖笔期间不盖文档分辨率的那一遍（本版核心）

一笔实际要盖两遍：

- **文档缓冲**（4096×4096，最终要写进图层的那一份）
- **屏幕预览**（用户此刻真正看到的）

拖笔时两遍都盖，等于每一滴都是双份成本。但文档那一遍在抬手之前根本没被看到 —— 它只是为「抬手后合成」做准备。

所以现在：拖笔时只盖屏幕预览，同时把每一滴的坐标和笔头记进一个数组；抬手时在 `commitBrushStroke` 里按同一组坐标、同一个笔头一次补进文档缓冲（新函数 `replayDocDabs`）。

- 结果完全一致：同一批坐标、同一个笔头、同一个透明度，不是「近似」，是同一组数据补画。
- 只在这种情况启用（`deferDocStamp`）：`deferLive` 已满足（大图/视口大 + 纯画笔 + 无选区 + 无渐隐 + 正常混合），再加「无散点、无抖动、无大小抖动、无角度抖动、角度 0、圆度 1」—— 否则每一滴长得都不一样，补画会跟预览不一致。
- 不满足条件时退回原路（两遍都盖），行为与 0.67.78 相同。

拖笔期间成本从「2 次 drawBitmap」降到「1 次」，加上笔头减半，一次移动的盖章时间大约是原来的 1/4。抬手时补画一次（几百滴，几十毫秒），用户感知不到。

## 怎么验

1. 4096 图上画一笔长线（和上次一样的动作）：应该明显更跟手。
2. 抬手看结果：笔迹应该没有断裂、没有变淡、没有重复加深（补画是同一组坐标，理论上完全一致）。
3. 打开日志：`盖章` 那一项应该只有原来的一半（文档那一遍不计入了），`笔头` 约 550~650。
4. 换一支带抖动/散点的笔：会退回两遍都盖的路径，行为跟上一版一样。
