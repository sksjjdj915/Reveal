# 0.67.88 修复记录（2026-11-08）

## 结论：动感模糊那次不是「Java 崩溃」，是被系统当「无响应」杀掉了

证据（`Reveal日志-1108-2326.txt`）：

```
[11-08 23:25:40] filter   name=动感模糊 depth=8
[11-08 23:25:50] APP START   v=0.67.87     ← 10 秒后自己重启，中间什么都没有
```

- 滤镜**开始了**（`filter` 那条写进去了），但没等到「完成」，10 秒后进程被系统重建；
- 「崩溃」页里空 —— 因为进程被杀（ANR / 系统回收）时，Java 的未捕获异常处理器**根本不会执行**；
- 10 秒这个数字正好是 Android 的 ANR 判定区间。

根因：`SketchView.applyFilterToActive()` 把整幅像素的滤镜**跑在主线程上**，1080×1620 就是 175 万像素逐像素算，
主线程卡住 → 系统弹不出「无响应」对话框（我们在全屏绘制）→ 直接杀进程。

## 这次改了什么

`applyFilterToActive()` 整段重写：

1. 主线程只做两件事：拍一张图层快照、弹「正在应用 XXX…」；
2. 真正算滤镜、拼选区、生成结果位图，全在**后台线程**；
3. 算完 `post { }` 回主线程才换像素、记撤销、`dropMips()`、刷新；
4. 全程 `try/catch(Throwable)`：
   - 失败（包括 OOM）写一条 `filter 失败` 进诊断日志，带异常类名、message 和完整堆栈；
   - 画面上弹「XXX 失败：OutOfMemoryError（详情看首页日志）」；
5. 成功时提示改成「动感模糊 已应用（1234 ms）」，耗时直接看得见；
6. 开跑前记录一行 `filter name=… size=WxH 堆 已用/上限 MB`，下次再有问题能判断是不是内存。

## 怎么验

1. 打开 1080×1620 的图 → 滤镜 → 动感模糊 → 调参数 → 确定；
2. 界面**不应该卡住**，应该立刻出现「正在应用动感模糊…」，一两秒后提示「已应用（xxxx ms）」，图层变成模糊效果；
3. 如果还是失败，去首页「日志」→ **诊断** 页，会有一行 `filter 失败` 带堆栈；「崩溃」页则用来抓真正的 Java 崩溃。

## 还没做

- 滤镜没有进度条（只有「正在应用」这句话），大图不知道还剩多久；
- 滤镜期间没有禁用画布，如果这期间再动笔可能和结果打架（下一步加个「应用中」锁）。
