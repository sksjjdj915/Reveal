# 0.74.10 色相饱和度跟手 / 全图饱和度生效 / 色彩平衡能动

## 一、全图饱和度「没反应」的两层原因
1. **算法层**：原来全图通道也走逐像素 HSV —— `S = S * (1+sat/100)`。插画大多是高饱和像素，`S` 本来就接近 1，再乘很快就撞上限被截断，所以拉滑块几乎看不出变化。
2. **性能层**：逐像素 `Color.colorToHSV` + `Color.HSVToColor`（每像素两次 JNI 调用）在 480px 预览上就要 100~200ms 一次，拖动时预览泵排不上队，表现就是卡、不跟手。

### 改法（参考文献与安卓成熟做法）
- 全图通道、且六个色相带都没动时，改走 **`android.graphics.ColorMatrix` + `ColorMatrixColorFilter`**：把「饱和度 / 色相旋转 / 明度」合成一个 4×5 矩阵，由 `Canvas.drawBitmap` 交给 GPU 画一遍（Android 官方 `ColorMatrix` 文档就是这么用的）。
  - 饱和度用**亮度加权线性变换**（Rec.709：0.2126 / 0.7152 / 0.0722），这是跨平台通用的 satuation matrix（Skia / CSS filter 同源），拉开时不会像 HSV 那样一拉就撞顶，滑块手感线性。
  - 色相旋转用绕亮度轴的旋转矩阵（W3C filter 的 `hue-rotate` 同一套系数）。
  - 明度是整幅加减偏移（−100~100 → ±128）。
- 只要有任何一个色相带非零，或开了「着色」，仍走原来的逐像素 HSV 精确路径（带余弦窗权重），保证色带语义不变。

## 二、色彩平衡「调了没反应」
真因和上次色相带一样：`cr/mg/yb` 是 `remember { FloatArray(3) }`，滑块写 `cr[range] = it`，改的是数组内部元素，**Compose 感知不到**；旁边的 `ver++` 也没被任何地方读取，等于没触发重组，预览泵快照一直是旧的。
改法：三个数组换成 `mutableStateListOf(0f,0f,0f)`，滑块直接 `cr[range] = it` 就会触发重组；删掉没用的 `ver`。

## 三、没做（下一步按顺序）
自然饱和度的卡顿（同样是逐像素，但要先做 HSV→亮度加权的近似快路径）、照片滤镜跟手（改 ColorMatrix 叠加）、渐变映射补齐参数（先查桌面端的渐变映射参数表再定）。
