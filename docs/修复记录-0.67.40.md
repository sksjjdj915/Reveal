# Reveal 0.67.40 修复记录（性能：崩溃 / 打开慢 / 缩放卡）

对应反馈：05（三组三十层）打开约 1 分钟、缩放卡顿；10（4096 大图）打不开。

## 一、4096 打不开（崩溃）

**现象**：打开 37.8MB 的 4096 PSD 直接失败。

**日志**：`NoSuchMethodError: No virtual method get(I[BII)Ljava/nio/ByteBuffer; in class Ljava/nio/MappedByteBuffer`。

**原因**：`image/PsdIo.kt` 的 `copyRange()` 用了
`m.get(起始位置, 数组, 偏移, 长度)` —— 这个「绝对位置批量读」重载是 **Java 13** 才加的，
部分 Android ROM 上没有实现，一调用就 `NoSuchMethodError`。之前只有超过 24MB 的文件走内存映射，
所以小文件一直没暴露。

**改法**：换成 `duplicate()` + 相对位置 `get()`（API 1 就有，等价）：

```kotlin
val d = m.duplicate()
d.position(s)
d.get(out, 0, n)
```

## 二、打开慢

**原因（主要）**：工程存盘是「一边 PNG 编码一边往 zip 里写」，30 层就是 30 次**串行** PNG 编码
（`ProjectStore.save`，PNG 质量 100）。手机上单层 1200×900 大约几十到一百毫秒，三十层叠起来就是好几秒，
再加上解析、缩略图合成，观感就是一分钟。

**改法**：
1. 先**并行**把每层的 PNG（以及蒙版、智能对象原图）编码到内存（线程数 = CPU 核数，限制 2~4），
   再顺序写进 zip —— 格式没变，老工程照样能读。
2. 加了分段计时日志，把剩下的时间也能看见：

```
RevealPerf: import xxx.psd 6144KB layers=30 parse=...ms save=...ms
RevealPerf: save layers=30 1200x900 encode=...ms zip=...ms thumb=...ms total=...ms
RevealPerf: load <id> layers=30 ...ms
```

## 三、缩放卡

**原因**：合成缓存是在**视图空间**烘焙的（`SketchView.ensureComposite()` 里 `cc.concat(viewMatrix)`），
贴回屏幕时靠 `viewMatrix × cacheMatrix⁻¹` 复用，但复用的窗口写死为 0.97~1.34。
缩小方向每一步都会掉出这个窗口 → 三十层整体重合成一遍 → 掉帧。

**改法**：手势进行中（`zooming`）把窗口放宽到 0.42~2.4，先拿缓存顶着；
手指抬起、`zooming` 变 false 的那一帧自动按新倍率重建一次（保持清晰）。

参考：Krita 的瓦片 + mipmap 金字塔、GIMP 的 GimpProjection 金字塔提交，都是「投影缓存 + 只在必要时重算」。

## 四、验收

1. 打开 `Reveal-测试PSD\10_大图4096.psd`（37.8MB）——应该能打开，不再失败。
2. 打开 `05_三组三十层.psd` —— 明显比 0.67.39 快（并行编码生效）。
3. 三十层那张上双指连续缩放 —— 应该跟手，不再一顿一顿。
4. 缩放停下后画面应恢复清晰（手势结束会重建一次）。
5. 首页看缩略图、切换工程、撤销重做不受影响。

## 五、没做 / 下一步

- **没有换存储格式**：原计划把 PNG 换成 raw deflate，考虑到改格式要同时改读取端、且老工程必须能读，
  风险大于收益，这版先做并行编码。等计时日志数据出来再决定。
- **没有上瓦片系统**：Krita 那种 64×64 瓦片 + 分层金字塔是彻底方案，工作量在一周以上，暂不做。
- 如果日志显示 `parse` 仍然占大头，下一步做「解析时按层并行 / 懒解码」（打开只解可见层）。
